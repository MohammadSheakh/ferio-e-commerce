### Why duplicate customer records were being created

We analyzed the backend service logic (`ferio-nest-prisma`) and found **two root causes**:

1. **Order Checkout Lookup Bug (`OrderService.resolveCustomer`):**
   - Previously, when an order was placed, the system searched for existing customers by phone number using `take: 2`.
   - If `candidates.length !== 1` (e.g. if 0 matches or more than 1 match existed), it **bypassed existing profiles and created a brand new `Customer` record** with the same name, email, and phone!

2. **Address & Account Linking (`CustomerAccountService.ensureCustomerForUser`):**
   - When a registered user added a shipping address or updated their account details for the first time, `ensureCustomerForUser` checked if `user.customerId` was set.
   - If not set, it directly called `customer.create(...)` without checking if a customer with that user's email or phone number already existed in the database.

---

### Fixes Applied to Backend (`ferio-nest-prisma`):

1. **`src/features/order/order.service.ts`:**
   - Updated `resolveCustomer` to search for existing customers by `phoneNormalized` **or** `email` (`findFirst`).
   - Reuses and updates the existing customer record rather than creating duplicate profiles during checkout.

2. **`src/features/customer-account/customer-account.service.ts`:**
   - Updated `ensureCustomerForUser` to check if a customer record matching the user's `email` or `phoneNormalized` already exists.
   - Automatically links `User.customerId` to the existing customer profile instead of spawning a new duplicate record.

Both changes have been built and verified (`pnpm --filter ferio-nest-prisma build` completed with Exit Code 0). Future registrations and orders will now properly reuse existing customer profiles.

### 🚀 Found & Fixed the Exact Frontend Proxy Issue

#### 🔍 Root Cause of the Rider Portal Login Error:
The `/delivery/portal` page was originally posting login requests to `/api/account/login` (the Customer Web session proxy). 
1. Customer auth proxy (`/api/account/login`) stores the JWT `accessToken` inside an **HTTP-only cookie** (`ferio_session`) and returns `{ data: user }` **without** an `accessToken` field in the JSON payload.
2. The Rider Portal page expected `{ accessToken: "..." }` in the JSON response to store in `localStorage` for its bearer-authenticated API requests (`/delivery-personnel/my-orders` and `/delivery-personnel/location`).
3. Because `data.accessToken` was `undefined`, the frontend threw a validation error (`"Rider login failed. Check credentials."`) even when the credentials were correct!

---

### 🔧 Fix Applied:

1. **Created Dedicated Rider Login Proxy Route (`/api/delivery/login`):**
   - File: `ferio-customer-web/app/api/delivery/login/route.ts`
   - Proxies authentication directly to NestJS `/auth/login` and explicitly returns the `{ accessToken, user }` JSON payload required by the Rider PWA.

2. **Updated Rider Portal (`/delivery/portal`):**
   - Pointed form submit handler to `/api/delivery/login`.
   - Properly receives `accessToken`, saves it in `localStorage` as `ferio_rider_token`, and authenticates the session seamlessly.
