# Lesson 8 — Redis, BullMQ, Background Jobs & WebSockets ⚡

Now we leave the normal database world and learn how Ferio handles **fast temporary data, work that happens later, and live updates**.

First, keep this picture in your head:

```text
PostgreSQL = permanent business memory 🧠
Redis      = super-fast temporary memory ⚡
BullMQ     = job/task system 📋
WebSocket  = live connection 🔌
```

These are **not four competing databases**. They solve different problems.

---

# 1. Start with PostgreSQL

You already know this one.

ABC Electronics has important data:

```text
Customers
Products
Orders
Payments
Inventory
Returns
Refunds
Settings
```

These belong in:

```text
ABC PostgreSQL Database
```

Why?

Because if the server restarts tonight, tomorrow ABC still needs:

```text
Order #1001
Nadia
৳115,100
DELIVERED
```

So think:

> PostgreSQL = the official record.

---

# 2. Then why do we need Redis?

Imagine Ferio constantly needs tiny pieces of information:

```text
OTP codes
Cache
Temporary session information
Rate-limit counters
Queue information
Short-lived state
```

You *could* keep hitting PostgreSQL for every tiny thing.

But sometimes that's unnecessarily expensive or slow.

Redis is designed for extremely fast access to data, commonly in memory.

Baby analogy:

### PostgreSQL = filing cabinet

You carefully store official documents.

```text
🗄️
Order
Invoice
Customer
Payment
Inventory
```

### Redis = desk

Things you're actively using:

```text
📝 OTP
📝 cache
📝 temporary counter
📝 queue information
```

You can grab them very quickly.

---

# 3. Example: OTP

Nadia requests:

```text
Login OTP
```

Ferio generates:

```text
482917
```

It only needs to live for perhaps a few minutes.

You don't necessarily want a permanent business record saying:

```text
OTP 482917
created 3:31 PM
...
```

forever.

Redis can conceptually store:

```text
OTP:NADIA = 482917

expires in 5 minutes
```

After expiration:

```text
gone
```

Redis is very good at this kind of temporary state.

---

# 4. Redis can expire things automatically

This concept is called:

```text
TTL
```

**Time To Live**

Example:

```text
Key:
otp:user123

Value:
482917

TTL:
300 seconds
```

After:

```text
300 seconds
```

Redis removes/expires it.

So:

```text
SET
 ↓
exists
 ↓
TTL runs out
 ↓
gone
```

---

# 5. Redis cache

Suppose ABC's settings are requested constantly:

```text
Store name
Currency
Checkout configuration
Theme setting
```

Instead of repeatedly doing:

```text
Request
 ↓
PostgreSQL

Request
 ↓
PostgreSQL

Request
 ↓
PostgreSQL
```

Ferio can sometimes cache appropriate data:

```text
First request
      ↓
PostgreSQL
      ↓
Redis cache
```

Later:

```text
Request
   ↓
Redis
   ↓
Found!
   ↓
Return quickly
```

This is:

```text
CACHE HIT
```

If Redis doesn't have it:

```text
CACHE MISS
```

then:

```text
Redis miss
    ↓
PostgreSQL
    ↓
get data
    ↓
possibly cache it
    ↓
return
```

# 6. The huge SaaS danger: Redis also needs tenant isolation

This is VERY important for Ferio.

Imagine this Redis key:

```text
settings
```

ABC visits first.

Redis stores:

```text
settings =
{
  storeName: "ABC Electronics"
}
```

Then Perfect Textile requests settings.

Backend asks:

```text
Redis → give me "settings"
```

Redis responds:

```text
ABC Electronics
```

💥

Perfect Textile just received ABC's cached data.

---

# 7. Tenant-scoped Redis keys

Instead, Ferio needs trusted tenant identity in tenant-specific keys.

Conceptually:

```text
tenant:ABC:settings
```

and:

```text
tenant:PERFECT:settings
```

Now:

```text
ABC
 ↓
tenant:ABC:settings
```

while:

```text
Perfect
 ↓
tenant:PERFECT:settings
```

No collision.

Your MT-8 implementation specifically prefixes tenant-scoped Redis data using trusted tenant identity, including settings, OTP and user-profile/stat caches. 

---

# 8. Same username doesn't matter

Suppose both businesses have:

```text
userId = 123
```

Bad:

```text
user:123:profile
```

because both tenants could collide.

Better conceptual namespace:

```text
tenant:ABC:user:123:profile

tenant:PERFECT:user:123:profile
```

The tenant identity becomes part of the namespace.

Remember:

> **Database-per-tenant does NOT automatically protect Redis.**

PostgreSQL is isolated because ABC and Perfect use different DBs.

But Redis may be shared infrastructure.

Therefore **you must create isolation yourself**.

# 9. Now BullMQ 📋

Suppose Nadia places an order.

The database transaction succeeds:

```text
Order #1001
CONFIRMED
```

Now Ferio needs to:

```text
Send SMS
Send email
Send WhatsApp
Update some analytics
Perform other asynchronous work
```

Should Nadia's browser wait for everything?

Imagine:

```text
Place Order
   ↓
create DB order        200ms
   ↓
send SMS               2 sec
   ↓
send WhatsApp          3 sec
   ↓
send email             2 sec
   ↓
analytics              1 sec
   ↓
finally respond
```

Customer waits:

```text
8+ seconds 😐
```

Bad.

---

# 10. Queue the work

Instead:

```text
PLACE ORDER
      ↓
Save critical order
      ↓
COMMIT
      ↓
Add notification job
to queue
      ↓
Return success
```

Customer quickly sees:

```text
Order placed successfully! ✅
```

Meanwhile:

```text
BACKGROUND
    ↓
Worker receives job
    ↓
Send notification
```

That's the basic reason for BullMQ.

---

# 11. What is a Queue?

Imagine a restaurant.

Orders arrive:

```text
Burger
Pizza
Pasta
Burger
```

Chef cannot cook everything at literally the same instant.

So tickets wait:

```text
┌────────────────┐
│ Job 1: SMS     │
│ Job 2: Email   │
│ Job 3: WhatsApp│
│ Job 4: Report  │
└────────────────┘
```

That's the **queue**.

Then workers take jobs.

```text
QUEUE
 │
 ├── Job A → Worker
 ├── Job B → Worker
 └── Job C → Worker
```

---

# 12. BullMQ and Redis relationship

This often confuses beginners.

BullMQ isn't the same thing as Redis.

Think:

```text
BullMQ
=
the job/queue system
```

and:

```text
Redis
=
infrastructure BullMQ uses to hold/manage
queue state
```

Simplified:

```text
NestJS
  │
  ▼
BullMQ Queue
  │
  ▼
Redis
  ▲
  │
BullMQ Worker
  │
  ▼
Do the job
```

# 13. Producer and Worker

You'll hear two useful concepts.

### Producer

Creates/adds a job.

```text
Order confirmed
      ↓
Producer
      ↓
"Send confirmation to Nadia"
```

### Worker

Processes the job.

```text
Queue
  ↓
Worker
  ↓
Send message
```

So:

```text
PRODUCER
=
"Please do this."


WORKER
=
"Okay, I'm doing it."
```

# 14. Real Ferio example

Nadia's order commits.

Conceptually:

```text
OrderService
     ↓
COMMIT
     ↓
TransactionalMessagingService
     ↓
Queue job
```

Job might conceptually contain trusted context like:

```text
organizationId: ABC
messageId: MSG_123
```

Then later:

```text
Worker
   ↓
organizationId = ABC
   ↓
resolve ABC tenant
   ↓
ABC database
   ↓
load message/order
   ↓
send it
```

Your implementation already makes transactional messaging tenant-aware and fans background work out across READY/ACTIVE tenants. 

---

# 15. BullMQ has the SAME tenant problem

Imagine a job says only:

```text
orderId = 1001
```

ABC has:

```text
Order #1001
```

Perfect also has:

```text
Order #1001
```

Which one?

😬

A background worker doesn't have:

```text
Host: abc.ferio.com
```

like an HTTP request does.

That's a huge insight.

---

# 16. HTTP knows the hostname — background jobs don't

Normal request:

```text
abc.ferio.com
      ↓
Tenant Resolver
      ↓
ABC
```

But hours later, worker gets:

```text
process order 1001
```

There is no browser.

There is no:

```text
abc.ferio.com
```

So the job itself needs trusted tenant information.

Conceptually:

```text
Job
{
   organizationId: ABC,
   orderId: 1001
}
```

Then worker can do:

```text
organizationId
      ↓
validate tenant
      ↓
resolve database
      ↓
ABC DB
```

---

# 17. This is called a trusted job envelope

Think of an envelope:

```text
┌──────────────────────────┐
│ TO: ABC ELECTRONICS      │
│                          │
│ Job: process order 1001  │
└──────────────────────────┘
```

Without tenant identity:

```text
┌──────────────────────────┐
│ Job: process order 1001  │
└──────────────────────────┘

Which business? 🤷
```

Your architecture propagates organization identity in the job envelope and resolves the correct tenant before processing.

This is basically:

```text
TenantContext
```

for background work.

---

# 18. Job IDs should also be tenant-scoped

Imagine both tenants create:

```text
jobId = reconcile-2026-09-08
```

If the queue treats IDs globally, they could collide.

Better:

```text
ABC:reconcile:2026-09-08

PERFECT:reconcile:2026-09-08
```

Same principle again:

> Tenant identity must follow the data everywhere.

Not just PostgreSQL.

---

# 19. What happens when a job fails?

Suppose:

```text
Send WhatsApp
```

fails because provider is temporarily down.

You don't necessarily want:

```text
FAILED
 ↓
forget forever
```

BullMQ can support retry behavior.

Conceptually:

```text
Attempt 1
   ↓
FAIL

wait

Attempt 2
   ↓
FAIL

wait longer

Attempt 3
   ↓
SUCCESS ✅
```

This is why background jobs are useful for unreliable external services.

---

# 20. Backoff

You'll see the word:

```text
backoff
```

It simply means:

> Don't hammer the failing service immediately over and over.

Bad:

```text
FAIL
retry
FAIL
retry
FAIL
retry
FAIL
retry
```

Better:

```text
FAIL
 ↓
wait
 ↓
retry
 ↓
FAIL
 ↓
wait longer
 ↓
retry
```

---

# 21. Idempotency returns again!

Remember Lesson 7?

Suppose worker sends:

```text
"Your order is confirmed."
```

Worker crashes at a bad moment.

BullMQ retries.

You don't want Nadia receiving:

```text
Your order is confirmed.
Your order is confirmed.
Your order is confirmed.
Your order is confirmed.
```

So background processing often needs idempotency too.

Same principle:

```text
Retry safely
without duplicating business effects.
```

This is why I said idempotency will appear everywhere.

# 22. Now WebSockets 🔌

Normal HTTP works like:

```text
Browser:
"Hey server, give me order status."

Server:
"SHIPPED."

connection/request finishes.
```

Later browser wants new status:

```text
Browser:
"Anything changed?"

Server:
"OUT_FOR_DELIVERY."
```

That's request/response.

But what if Ferio needs **live updates**?

For example:

```text
Rider moves
    ↓
Admin map should move immediately
```

Or:

```text
New chat message
    ↓
Other person sees it instantly
```

This is where WebSockets become useful.

---

# 23. HTTP vs WebSocket

Think of HTTP like texting a shop:

> You: What's my order status?

> Shop: Shipped.

Conversation ends.

You ask again later.

WebSocket is more like keeping a phone call open:

```text
Browser ←────────────→ Server
       live connection
```

Now server can push something immediately:

```text
Server:
"Rider moved."

Server:
"New message."

Server:
"Order changed."
```

without waiting for the browser to start a brand-new normal request each time.

# 25. WebSocket rooms

Imagine Ferio has thousands of connected clients.

You don't want every update sent to everyone.

WebSocket systems often group connections into:

```text
rooms
```

Example:

```text
room:
order:1001
```

People watching Order #1001 can join that room.

Then:

```text
Server
   ↓
emit to order:1001
   ↓
only interested clients receive it
```

# 28. How does WebSocket know the tenant?

HTTP had:

```text
hostname
 ↓
Tenant Resolver
```

Socket connection also needs trusted authentication/tenant resolution when connecting.

Conceptually:

```text
Client connects
      ↓
Authenticate socket
      ↓
Resolve tenant
      ↓
Tenant = ABC
      ↓
Issue/validate trusted socket identity
      ↓
Join ABC-scoped rooms
```

After that, the socket should not simply claim:

```text
"Actually I'm Perfect now."
```

😂

Tenant identity must remain trusted.

# 29. PostgreSQL vs Redis vs BullMQ vs WebSocket

This table is worth memorizing:

| Technology | Think of it as                   | Ferio example        |
| ---------- | -------------------------------- | -------------------- |
| PostgreSQL | Permanent official memory        | Orders               |
| Redis      | Very fast temporary/shared state | OTP/cache            |
| BullMQ     | Background task queue            | Send message         |
| Worker     | Person doing queued job          | Process notification |
| WebSocket  | Live connection                  | Rider/chat updates   |

# 31. The most important SaaS lesson in MT-8

You can perfectly isolate PostgreSQL and **still build an insecure SaaS**.

Imagine:

```text
ABC DB        Perfect DB
  ✅ isolated ✅
```

but then:

```text
Redis key:
settings
❌
```

or:

```text
BullMQ job:
orderId=1001
❌
```

or:

```text
WebSocket room:
order:1001
❌
```

You've just recreated cross-tenant leakage outside PostgreSQL.

Therefore Ferio must isolate **every shared infrastructure layer**:

```text
Database
Cache
Queues
Jobs
Sockets
Files
External credentials
Logs
Audit
```

That's exactly why MT-8 exists.

# 34. One request can cross many systems

This is the part I want you to really understand.

Nadia places one order.

It might touch:

```text

      ↓
TenantContext
      ↓
ABC PostgreSQL
      ↓
BullMQ job
      ↓
Redis
      ↓
Worker
      ↓
Messaging provider
      ↓

      ↓
```

At **every arrow**, Ferio needs to preserve:

```text

```

You can imagine an invisible sticker traveling everywhere:

```text

```

That's the real idea behind multi-tenant infrastructure.
