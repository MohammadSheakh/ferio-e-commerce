# Lesson 10 — Production: How Ferio Goes Live 🚀

This is the final lesson of our original 10-lesson foundation.

So far, you've learned how Ferio works **inside the code**. Now imagine you finish coding and say:

> "Okay... how do real customers actually use this?"

That's production.

---

# 1. Development vs Production

Right now, when developing Ferio, you might have something like:

```text
Your Ubuntu PC
│
├── Customer Web
├── Tenant Admin
├── Platform Admin
├── NestJS Backend
├── PostgreSQL
└── Redis
```

Maybe you run commands like:

```bash
pnpm dev
```

or:

```bash
nest start --watch
```

That's **development**.

Real customers can't depend on your laptop staying on.

Production means Ferio runs on infrastructure intended to be continuously available:

```text
Internet
   ↓
Cloudflare / DNS
   ↓
Ferio production infrastructure
   │
   ├── Next.js Storefront
   ├── Tenant Admin
   ├── Platform Admin
   ├── NestJS API
   ├── Workers
   ├── PostgreSQL
   ├── Redis
   └── Object Storage
```

# 2. What does Docker do? 🐳

You've already seen Docker in your project.

Imagine NestJS needs:

```text
Node.js
Dependencies
Environment configuration
Application files
System libraries
```

You don't want production deployment to become:

> "It works on my PC but not on the server."

Docker packages the application's runtime environment into a reproducible container image.

Think of a shipping container:

```text
┌──────────────────────────┐
│      NESTJS CONTAINER    │
│                          │
│ Node                     │
│ compiled application     │
│ dependencies             │
│ required runtime pieces  │
└──────────────────────────┘
```

Then another:

```text
┌──────────────────────────┐
│ CUSTOMER WEB             │
│ Next.js                  │
└──────────────────────────┘
```

and perhaps another:

```text
┌──────────────────────────┐
│ WORKER                   │
│ BullMQ processors        │
└──────────────────────────┘
```

Docker gives you a predictable unit to deploy.

# 3. Docker Compose

During development or simpler deployments, Docker Compose can describe several services together.

Conceptually:

```text
docker-compose.yml

        │
        ├── NestJS
        ├── Customer Web
        ├── Tenant Admin
        ├── Platform Admin
        ├── PostgreSQL
        └── Redis
```

Then:

```bash
docker compose up
```

can start the defined stack.

Think:

> **Docker = one packaged service/container.**

> **Docker Compose = instructions for running a group of containers together.**

# 5. CI/CD

You'll hear this constantly.

Very simplified:

### CI — Continuous Integration

```text

   ↓

   ↓

```

For example:

```text

```

If something fails:

```text

```

If everything passes:


After successful validation:

```text

      ↓

      ↓

      ↓
```

# 7. What is a database migration?

Suppose every tenant currently has:

```text
Order
────────────────
id
total
status
```

You build a new feature requiring:

```text
Order
────────────────
id
total
status
source
```

The code expects:

```text
source
```

but old databases don't have that column.

So you need a migration.

```text
OLD DATABASE
     ↓
migration
     ↓
NEW DATABASE STRUCTURE
```

---

# 8. In single-tenant Ferio this was easier

Before SaaS:

```text
Migration
    ↓
one database
    ↓
done
```

With database-per-tenant:

```text
Migration
    ↓
ABC DB
Perfect DB
Baby Shop DB
XYZ DB
...
```

That's called a **fleet migration** problem.

Your checklist gives MT-11 specifically to tenant migration orchestration, after the tenant DB/provisioning foundations. 

---

# 9. Why not migrate all tenants at once?

Imagine Ferio has:

```text
1,000 tenant databases
```

You release migration:

```text
ALTER SOMETHING...
```

and immediately run:

```text
ALL 1,000 DATABASES
AT ONCE
```

Then migration contains an unexpected problem.

💥

You potentially damaged or interrupted:

```text
1,000 businesses
```

at once.

That's called a huge **blast radius**.

---

# 10. Canary migration 🐤

Instead, start tiny.

```text
New migration
     ↓
Canary tenant
```

Maybe one controlled/internal tenant.

Check:

```text
Did migration succeed?
Does app work?
Any errors?
Performance okay?
```

If bad:

```text
STOP ❌
```

You protected the rest of the fleet.

If good:

```text
continue
```

---

# 11. Then batches

Instead of:

```text
1 → 1000
```

do something conceptually like:

```text
Canary
  ↓
small batch
  ↓
check
  ↓
another batch
  ↓
check
  ↓
larger fleet
```

Think of giving a new medicine:

```text
Don't give it to 1,000 people
before discovering the first person
has a serious problem.
```

Same risk-control concept.

Your current migration orchestrator is BullMQ-backed and includes canary/batch progression, per-tenant results, transient retry, failure-threshold pause and queued resume. 

---

# 12. Failure isolation

Imagine batch:

```text
ABC       ✅
Perfect   ✅
BabyShop  ❌
Fresh     ✅
Titan     ✅
```

Bad migration system:

```text
BabyShop failed
      ↓
everything becomes chaos
```

Better:

```text
BabyShop
   ↓
FAILED
   ↓
record failure

Other safe tenants/results
remain independently tracked
```

Depending on your configured failure threshold, the orchestrator can pause before exposing more tenants.

Your tests cover isolated tenant failure and threshold-based pause/resume behavior. 

---

# 13. Schema version

Ferio needs to know something like:

```text
ABC DB
schema version = X

Perfect DB
schema version = X

BabyShop DB
schema version = X-1
```

because maybe Baby Shop's migration failed.

Your Control Plane models tenant database schema version/readiness and migration runs/results. 

So the Control Plane isn't storing Baby Shop's orders.

It's storing information **about Baby Shop's database**.

Exactly like Lesson 3.

---

# 14. Expand → Migrate → Contract

This is a useful production migration pattern.

Suppose you want to replace:

```text
oldField
```

with:

```text
newField
```

Dangerous idea:

```text
delete oldField
      ↓
deploy code using newField
```

During rollout, some old code may still expect `oldField`.

Instead, safer evolution often looks like:

```text
EXPAND
   ↓
add new structure
without immediately breaking old code

MIGRATE
   ↓
move/backfill data
and transition application behavior

CONTRACT
   ↓
remove old structure
only when it is no longer needed
```

Think:

```text
Old bridge
   +
New bridge

↓ move traffic

New bridge

↓ only then

remove old bridge
```

Much safer.

```text

  └── backup
```

But there's an extremely important lesson:

> **A backup is only useful if you can successfully restore it.**

# 16. Backup vs Restore

### Backup

```text
Database
   ↓
safe copy
```

### Restore

```text
safe copy
   ↓
working database
```

A company saying:

> "We have backups."

isn't enough.

You want evidence:

```text
backup
  ↓
restore test
  ↓
database starts
  ↓
data verified
  ↓
application works
```

Your launch checklist still marks backup/restore proof as unfinished. 

So this is important:

**Don't read the checklist as saying Ferio production readiness is already complete.**

Some major gates remain open.

---

# 17. Database-per-tenant gives Ferio a nice recovery property

Suppose only ABC has a problem.

Architecture:

```text
ABC DB       ❌ problem

Perfect DB   ✅
BabyShop DB  ✅
Fresh DB     ✅
```

Potentially, you can work on restoring ABC independently rather than restoring one enormous shared commerce database containing everyone.

That's one of the operational benefits of database-per-tenant isolation.

But it also means you now have many databases to back up, track and test.

Trade-off:

```text
Better isolation
       ↕
More operational complexity
```

Architecture always has trade-offs.

---

# 18. RPO

You may see:

```text
RPO
```

**Recovery Point Objective**

Simple meaning:

> How much recent data can we tolerate losing after a disaster?

Example only:

```text
Last usable recovery point:
3:00 PM

Database disaster:
3:20 PM
```

Potential data loss:

```text
20 minutes
```

RPO describes the acceptable recovery-point gap.

Smaller RPO:

```text
less acceptable data loss
```

usually means stronger/more frequent recovery infrastructure.

---

# 19. RTO

```text
RTO
```

**Recovery Time Objective**

Meaning:

> How long can the service remain unavailable before we need it restored?

Example:

```text
Failure:
3:00 PM

Service restored:
4:30 PM
```

Recovery time:

```text
1.5 hours
```

So remember:

```text
RPO
=
How much DATA can we lose?


RTO
=
How much TIME can we be down?
```

Very common interview/architecture terms.

# 22. Logs

Logs tell you what happened.

Example conceptually:

```text
INFO
order confirmed

WARN
usage threshold crossed

ERROR
payment webhook verification failed
```

For Ferio, logs become much more useful when they carry safe correlation context such as:

```text
organizationId
requestId
correlationId
jobId
```

Then when ABC says:

> "Checkout failed at 4:15 PM."

you can investigate ABC's request path instead of digging through millions of unrelated messages.

Remember from Lesson 2: your `TenantContext` is also intended to propagate safe correlation metadata through jobs, sockets, audits and logs.

---

# 23. But be careful with logs

Do NOT think:

```text
More logging = always better.
```

You shouldn't casually log:

```text

tokens ❌
```

Logs themselves are data that need security.

# 25. Health checks ❤️

Imagine a load balancer/server asks NestJS:

```text
Are you alive?
```

A basic health endpoint may answer:

```text
200 OK
```

But production health can be more nuanced.

You might care about:

```text
Is application process alive?
Can required infrastructure be reached?
Is DB pool healthy?
Is Redis available?
```

This leads to concepts such as:

```text
Liveness
Readiness
```

Very simplified:

```text
Liveness
=
"Am I alive?"


Readiness
=
"Am I ready to receive traffic?"
```

A process can technically be alive while not being ready to safely serve requests.

# 27. TLS / HTTPS 🔒

Customers should see:

```text
https://baby-shop.ferio.com
```

not insecure plain HTTP.

TLS gives you encrypted communication between client and the HTTPS endpoint.

For SaaS with many subdomains, certificate/domain automation becomes part of the operational architecture.

Your decision log records Cloudflare DNS, wildcard subdomains and automated TLS as the chosen direction.

# 28. Production secrets

Your application needs secrets such as:

```text
database credentials
encryption keys
payment-provider secrets
storage credentials
JWT/signing secrets
```

Do not put them into:

```text
GitHub repository ❌
frontend JavaScript ❌
hardcoded source code ❌
```

Production secrets belong in appropriate secure server-side configuration/secrets management.

Remember from earlier lessons:

> Tenant DB credentials must never be exposed to the frontend.

# 29. Rollback

Suppose:

```text
Ferio v1.8
```

works.

You deploy:

```text
Ferio v1.9
```

and suddenly checkout breaks.

You need an operational answer to:

> "How do we return to a known-safe state?"

That's rollback/recovery planning.

But database changes make this harder.

Application rollback:

```text
v1.9
 ↓
v1.8
```

may be easy.

Database rollback:

```text
new schema/data changes
 ↓
old schema
```

can be dangerous or destructive.

That's another reason for careful backward-compatible migrations like:

```text
expand
 ↓
migrate
 ↓
contract
```

instead of destructive changes immediately.

# 31. Internal Alpha

Before giving Ferio to real businesses, your checklist says to provision at least three internal tenants and intentionally use overlapping customer/product/order identifiers. 

Why intentionally overlapping IDs?

Suppose:

```text
Tenant A
Order #1001

Tenant B
Order #1001

Tenant C
Order #1001
```

Now try to break Ferio.

```text
Can A see B's order?
Can B receive C's socket event?
Can A's Redis cache affect C?
Can a background job resolve wrong tenant?
```

This is excellent SaaS testing.

You WANT collisions in testing.

Because they expose missing tenant scoping.
