# Lesson 2 — Follow ONE Request

This lesson is **extremely important**.

Suppose I visit:

```text
abc.ferio.com
```

and the website wants products.

The frontend eventually needs something equivalent to:

```http
GET /api/v1/catalog/products
```

The big question is:

> **How does the same NestJS backend know to return ABC's products rather than Perfect Textile's products?**

---

## Step 1 — Browser

Imagine Ferio has two businesses:

```text
abc.ferio.com

perfect.ferio.com
```

I visit:

```text
abc.ferio.com
```

My browser is basically saying:

```text
Hello Ferio.

Host = abc.ferio.com
I want products.
```

So conceptually:

```text
Browser
   │
   │ GET /products
   │ Host: abc.ferio.com
   ▼
NestJS
```

---

# Step 2 — NestJS receives it

Your NestJS backend is shared.

This is important.

You don't have:

```text
ABC NestJS
Perfect NestJS
Fashion NestJS
Electronics NestJS
```

You have:

```text
                 ONE NESTJS
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
         ABC      Perfect    Fashion
```

The same backend handles requests for different businesses. Your project map identifies `ferio-nest-prisma` as the shared NestJS backend. 

Therefore NestJS's first problem is:

> Which business sent this request?

---

# Step 3 — Tenant Resolver

This is where your:

```text
Tenant Resolver
```

comes in.

Imagine Nest receives:

```text
Host:
abc.ferio.com
```

The resolver extracts:

```text
abc
```

But it doesn't just blindly trust that string.

It asks the **Control Plane**:

```text
Do we have a tenant whose domain is
abc.ferio.com?
```

Conceptually:

```text
                 Control Plane DB

Organization
──────────────────────────────────
id      name              status
──────────────────────────────────
ORG_1   ABC Electronics   ACTIVE
ORG_2   Perfect Textile   ACTIVE


TenantDomain
──────────────────────────────────
hostname              organization
──────────────────────────────────
abc.ferio.com         ORG_1
perfect.ferio.com     ORG_2
```

The control plane has models for `Organization`, `TenantDomain`, `TenantDatabase`, subscription information and other platform metadata. 

So:

```text
abc.ferio.com
      ↓
TenantDomain lookup
      ↓
ORG_1
      ↓
ABC Electronics
```

Great.

Now Ferio knows:

> This request belongs to ABC Electronics.

---

# Step 4 — TenantContext is created

Ferio now needs to remember this information for the rest of the request.

That's where:

```text
TenantContext
```

comes in.

Imagine Ferio creates an invisible sticker:

```text
┌────────────────────────────┐
│ TENANT CONTEXT             │
│                            │
│ Organization: ABC          │
│ Organization ID: ORG_1     │
│ Database: DB_ABC           │
│ Host: abc.ferio.com        │
└────────────────────────────┘
```

Then sticks it onto the request.

Now everything processing that request can know:

```text
THIS REQUEST = ABC
```

Your implementation uses an immutable `TenantContext` backed by `AsyncLocalStorage`. 

We'll learn `AsyncLocalStorage` later.

For now:

> TenantContext = Ferio's trusted memory of which business the current request belongs to.

---

# Step 5 — Request reaches Catalog

Now imagine the request reaches:

```text
CatalogController
```

Something conceptually like:

```ts
@Get('products')
getProducts() {
    return this.catalogService.getProducts();
}
```

Don't worry about Nest syntax yet.

The controller's job is basically:

> Someone requested `/products`. Ask CatalogService for products.

So:

```text
HTTP Request
     ↓
CatalogController
     ↓
CatalogService
```

---

# Step 6 — CatalogService needs a database

Now CatalogService wants to do:

```text
Give me products.
```

But we have:

```text
ABC DB
Perfect DB
Fashion DB
BabyShop DB
...
```

So simply doing:

```ts
prisma.product.findMany()
```

with one global Prisma client would be dangerous.

Instead, the tenant-aware service obtains the database associated with the trusted tenant context.

Your checklist says the commerce services—including Catalog—resolve through `TenantDbService`. 

Think:

```text
CatalogService
      │
      ▼
TenantDbService

"Who is the current tenant?"
      │
      ▼
TenantContext

"ABC / ORG_1"
```

---

# Step 7 — TenantDatabaseManager

Now Ferio needs the actual Prisma client connected to ABC's database.

That's the job of the:

```text
TenantDatabaseManager
```

Think of it as a receptionist holding database keys.

```text
TenantDatabaseManager

ORG_1 → 🔑 ABC Database
ORG_2 → 🔑 Perfect Database
ORG_3 → 🔑 Fashion Database
```

CatalogService effectively says:

> Give me the DB connection belonging to ORG_1.

Manager finds ABC's registered database and provides the appropriate Prisma client.

Your implementation already has a bounded `TenantDatabaseManager`, including client limits, idle eviction, acquisition timeout and per-database circuit breaking. 

Ignore those advanced words for now.

Just remember:

> **TenantDatabaseManager = gives Ferio the correct database connection.**

---

# Step 8 — Prisma

Now we finally reach Prisma.

ABC's Prisma client performs something conceptually like:

```ts
db.product.findMany();
```

But `db` here means:

```text
ABC DATABASE
```

not:

```text
Ferio global database
```

So:

```text
ABC Database

Product
──────────────────
iPhone 17
Galaxy S26
Pixel
MacBook
```

is queried.

Perfect Textile might simultaneously have:

```text
Perfect Database

Product
──────────────────
Blue Polo
White Shirt
Denim Jeans
Jacket
```

Those are completely separate.

---

# Step 9 — Database answers

PostgreSQL returns:

```text
iPhone
Galaxy
Pixel
MacBook
```

Then:

```text
PostgreSQL
     ↑
Prisma
     ↑
CatalogService
     ↑
CatalogController
     ↑
NestJS
     ↑
Customer Web
```

The browser gets ABC's products.

# The entire journey

Memorize this:

```text
abc.ferio.com
       │
       ▼
   Customer Web
       │
       │ GET /products
       ▼
     NestJS
       │
       ▼
 Tenant Resolver
       │
       │ "abc.ferio.com = ORG_1"

 TenantContext
       │

CatalogController
       │
       ▼
 CatalogService
       │

```

That's **multi-tenancy**.

# Why this is safer

Suppose a hacker tries:

```http
GET /products?tenantId=PERFECT
Host: abc.ferio.com
```

The hacker is effectively saying:

> I'm on ABC's website, but please give me Perfect Textile's database.

Ferio should say:

```text
No.
```

The database identity comes from trusted server-side tenant resolution, not a query/body/header supplied by the browser. Your completion rules explicitly require that property. 

Therefore:

```text
?tenantId=PERFECT
```

must **not** control DB selection.

The trusted host says:

```text
abc.ferio.com
      ↓
ABC
      ↓
ABC DB
```

---

# One sentence you should remember

If someone asks you:

> "How does Ferio know which database to use?"

You should now be able to answer:

> **Ferio resolves the tenant from the trusted hostname, creates a TenantContext, and uses that context to route the request through TenantDbService/TenantDatabaseManager to the correct tenant PostgreSQL database.**

That's already a pretty solid explanation of your architecture.
