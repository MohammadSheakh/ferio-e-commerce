# 9. Race condition 😈

Now we'll introduce an important programming idea.

Suppose only:

```text
1 iPhone
```

exists.

Two customers press **Place Order at exactly the same time**.

```text
Nadia                     Ahmed
  │                         │
  │ stock?                  │ stock?
  ▼                         ▼
  1                         1

  "Great!"                  "Great!"
```

Both then subtract one.

You could end up with:

```text
Nadia order ✅
Ahmed order ✅

stock = -1 💥
```

This is called a:

# Race condition

Two operations race against each other while depending on shared state.

# 10. Transactions help protect critical operations

This is where a **database transaction** becomes important.

Baby analogy:

Imagine one cashier is changing something important in a notebook.

They put a sign:

```text
PLEASE WAIT
I AM FINISHING THIS OPERATION
```

The goal is that a set of related database changes behave safely together.

For example, confirming an order might need:

```text
Check stock
     ↓
Reserve stock
     ↓
Change order state
```

You don't want:

```text
Reserve stock ✅

SERVER CRASH 💥

Order state update ❌
```

leaving inconsistent records.

A transaction gives you the idea:

```text
ALL succeed
     ↓
COMMIT ✅


something fails
     ↓
ROLL BACK ❌
```

Your current tenant-safe inventory work uses serializable confirmation transactions on the resolved tenant client to preserve finite-stock concurrency guarantees.

For a complicated operation like checkout, it's often easier to think:


The central workflow coordinates the operation instead of making every lower-level domain service know everything about every other service.

```text

   ↓

   ↓

   ↓
```

```text
   ↓

   ↓
```

```text
   │
   ├── FAILED
   │      ↓
   │   retry safely
   │
   └── SUCCESS
          ↓
      Payment = PAID
          ↓
      Order confirmed
          ↓
      Fulfillment
```

Then shipping is basically back on the same general path.

# 49. Three concepts from this lesson matter enormously

When you later read complicated Ferio code, keep these three in your head:

```text
TRANSACTION
=
related DB changes succeed together
or fail together


IDEMPOTENCY
=
retrying the same logical operation
doesn't create duplicate effects


RACE CONDITION
=
two simultaneous operations compete
over shared state
```

These three concepts show up everywhere:

```text
Checkout
Payments
Inventory
Refunds
Reconciliation
Provisioning
BullMQ jobs
Webhooks
```
