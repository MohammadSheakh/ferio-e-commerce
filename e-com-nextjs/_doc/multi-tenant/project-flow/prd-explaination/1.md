# 4. Your most important architecture decision

There are several ways to build multi-tenant software.

Your project chose:

## Database per tenant

Meaning:

```text
                    FERIO
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓

     perfect_db     abc_db     fashion_db

      Products      Products     Products
      Orders        Orders       Orders
      Customers     Customers    Customers
      Wallet        Wallet       Wallet
```

The document's target architecture explicitly says there is **one isolated PostgreSQL database per tenant**. 

That's an extremely important thing to remember.

You did **NOT** primarily design this as:

```text
One huge database

products
--------------------
tenantId | product
A        | iPhone
B        | Shirt
C        | Laptop
```

Instead:

```text
Perfect Textile DB
    ↓
shirts
orders
customers

ABC Electronics DB
    ↓
phones
orders
customers
```

This gives you a very strong isolation boundary.

Here's the next scary-sounding term.


```text

TenantDatabase
Plan

SaasInvoice
UsageCounter
```

Those models are explicitly part of your control-plane schema.

# 8. Tenant DB vs Control Plane DB

This distinction is fundamental.

### Control Plane

Ferio itself needs this information:

```text

```

### Tenant Database

Perfect Textile itself owns:

```text

Returns
Riders
Reviews
Settings
```

So memorize:

```text

      =
Ferio manages the BUSINESS


TENANT DATABASE
      =
Business manages its STORE
```

# 10. What is `TenantContext`?

Think of a waiter carrying a table number.

Customer says:

> "One burger."

Kitchen asks:

> "For which table?"

Waiter has:

```text
TABLE 7
```

The kitchen doesn't ask the customer repeatedly.

Your `TenantContext` is similar.

Once Ferio establishes:

```text
This request belongs to ABC Electronics
```

it carries something conceptually like:

```ts
TenantContext {
    organizationId: "abc",
    databaseId: "db_abc",
    hostname: "abc.ferio.com",
    subscription: "ACTIVE"
}
```

through the request.

So downstream services know:

```text
CatalogService
      ↓

"This request = ABC"

OrderService
      ↓

"This request = ABC"

WalletService
      ↓

"This request = ABC"
```

Your implementation makes that context immutable and uses `AsyncLocalStorage`, specifically so application services don't repeatedly derive tenancy from the raw host. 

Don't worry about `AsyncLocalStorage` yet.

For now:

> **TenantContext = trusted label attached to the current request saying which business it belongs to.**

# 13. What is Provisioning?

Suppose a new company signs up:

> "I want a Ferio store."

Ferio cannot simply create a username.

It needs to build their little world.

Conceptually:

```text
Create Organization
       ↓
Reserve slug
       ↓
perfect.ferio.com
       ↓
Create database
       ↓
Run migrations
       ↓
Create default settings
       ↓
Create owner
       ↓
Test database
       ↓
Activate store
```

That is:

# Provisioning

Your checklist requires this to be **idempotent and resumable**.

Baby explanation of idempotent:

Suppose provisioning crashes here:

```text
Create organization ✅
Create domain       ✅
Create database     ✅
Run migration       ❌ CRASH
```

You press Retry.

Bad implementation:

```text
Create organization AGAIN
Create domain AGAIN
Create database AGAIN
```

💥

Good implementation:

```text
Organization already done → skip
Domain already done       → skip
Database already done     → skip

Continue:
Run migration
Seed
Health check
Activate
```

That's **idempotent/resumable provisioning**.

Your checklist says those steps are persisted and replay resumes safely rather than duplicating DB/domain creation.

# 15. Redis — why does tenancy matter there?

Suppose both stores have:

```text
settings cache
```

Bad Redis key:

```text
settings:store
```

Tenant A writes:

```text
settings:store = "Perfect Textile"
```

Tenant B writes:

```text
settings:store = "ABC Electronics"
```

Oops.

Now A could potentially receive B's cache.

Instead:

```text
settings:ORG_A:store

settings:ORG_B:store
```

Same idea with OTPs, jobs, locks, etc.

Your checklist says tenant-scoped keys should use trusted organization identity and already has collision tests for identical identifiers across organizations.

# 16. BullMQ

BullMQ is basically Ferio's:

> **"Do this work later" system.**

Customer places an order.

You don't necessarily want the HTTP request waiting while Ferio does:

```text
send email
send SMS
contact courier
reconcile payment
process notifications
```

Instead:

```text
Order created
     │
     ▼
   Queue
     │
     ▼
 BullMQ Worker
     │
     ▼
Do background work
```

But again:

**WHICH TENANT?**

So the job needs something like:

```text
organizationId = ABC
```

Then worker:

```text
job
 ↓
organizationId
 ↓
Control Plane
 ↓
Tenant database registry
 ↓
ABC DB
 ↓
process job
```

Your implementation already follows this pattern through `TenantFanoutService.forOrganization`, and job IDs are prefixed with `t:{orgId}:...`.

# 21. The golden security rule

If you remember only **one technical rule**, remember this:

```text
Tenant A
   X
   X  NEVER
   X
Tenant B
```

Ferio must never allow:

```text
A sees B product
A sees B customer
A sees B order
A spends B wallet
A receives B socket event
A runs B background job
A reads B file
A uses B payment credentials
```

That's why the document doesn't consider something "done" just because the feature works.

It considers it done when tenant routing, authorization, namespaces, failure isolation, cross-tenant tests, observability and frontend failure states all satisfy the boundary.
