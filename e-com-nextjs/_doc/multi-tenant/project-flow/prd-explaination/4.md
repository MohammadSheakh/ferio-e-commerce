## 1. First: what exactly is NestJS?

Your frontend might display:

```text
iPhone 17
৳120,000

[ Add to Cart ]
```

But the frontend shouldn't directly open PostgreSQL.

Instead:

```text
Frontend
    │
    │ "Give me products"
    ▼
  NestJS
    │
    │ "I'll get them."
    ▼
PostgreSQL
```

NestJS is basically the **backend application** sitting between your apps and your data/business logic.

For Ferio, several apps can talk to that backend:

```text
             Customer Web
                  │
             Tenant Admin
                  │
             Mobile App
                  │
             Rider Portal
                  │
                  ▼
          ┌──────────────┐
          │    NestJS    │
          │   BACKEND    │
          └──────┬───────┘
                 │
                 ▼
          Databases / Redis
          Queues / Providers
```

Your project identifies `ferio-nest-prisma` as this shared NestJS backend.

# 3. Controller = the waiter

Suppose browser requests:

```http
GET /api/v1/catalog/products
```

Somewhere you may have code conceptually like:

```ts
@Controller('catalog')
export class CatalogController {

  @Get('products')
  getProducts() {
    return this.catalogService.getProducts();
  }

}
```

Don't worry about syntax yet.

Read it like English:

```text
@Controller('catalog')

"I handle requests coming to /catalog."
```

Then:

```text
@Get('products')

"If someone GETs /catalog/products,
run this function."
```

Therefore:

```text
GET /catalog/products
        ↓
CatalogController
        ↓
getProducts()
```

### Restaurant analogy

Customer:

> "Burger please."

Waiter receives the request.

But the waiter normally doesn't cook the burger.

Similarly:

> **Controller receives HTTP requests, but shouldn't contain all your business logic.**

---

# 4. Service = the kitchen/manager

Controller says:

```ts
return this.catalogService.getProducts();
```

Meaning:

> "CatalogService, please do the actual work."

Conceptually:

```ts
@Injectable()
export class CatalogService {

  async getProducts() {

     // business logic

  }

}
```

Now:

```text
Browser
   ↓
Controller
   ↓
Service
```

The service handles things such as:

```text
Which products?
Are they active?
What filters?
What pagination?
Which database?
What business rules?
```

So remember:

```text
CONTROLLER
=
receives request


SERVICE
=
does the work
```

---

# 5. Why not put everything in Controller?

You technically could write something horrible like:

```ts
@Get('products')
async getProducts() {

   // find tenant
   // connect database
   // check subscription
   // validate filters
   // query products
   // calculate something
   // transform response
   // etc...
}
```

Then controllers become enormous.

Instead:

```text
Controller
   │
   ▼
Service
   │
   ├── business logic
   ├── call database
   └── other services
```

Much cleaner.

---

# 6. What is `@Injectable()`?

You'll see:

```ts
@Injectable()
export class CatalogService {
}
```

Baby explanation:

`@Injectable()` tells NestJS:

> **"Nest, you are allowed to create and manage this class for me and inject it where it's needed."**

Because Controller needs:

```text
CatalogService
```

You usually don't manually do:

```ts
const catalogService = new CatalogService();
```

NestJS manages that relationship.

This leads to a very important concept:

# Dependency Injection

---

# 7. Dependency Injection sounds scary but isn't

Suppose:

```text
CatalogController
```

needs:

```text
CatalogService
```

Then you might see:

```ts
constructor(
  private readonly catalogService: CatalogService,
) {}
```

Read that as:

> "Hey NestJS, CatalogController needs CatalogService."

Nest says:

> "Okay. I'll provide it."

So:

```text
CatalogController
        │
        │ needs
        ▼
CatalogService
```

That's dependency injection.

# 8. Another example

Suppose `CatalogService` needs:


You may see:

```ts
constructor(
  private readonly tenantDb: TenantDbService,

```

Meaning:


Nest provides it.

Now:

```text
CatalogController
       │
       ▼
CatalogService
       │
       ▼
TenantDbService
```

This is why constructors appear everywhere in NestJS.

# 9. Then what is a Module?

Now we have:

```text
CatalogController
CatalogService
```

How does NestJS know these belong together?

That's where:

```text
CatalogModule
```

comes in.

Conceptually:

```ts
@Module({
  controllers: [
    CatalogController
  ],

  providers: [
    CatalogService
  ]
})
export class CatalogModule {}
```

Think of a Module as a **box**.

```text
┌─────────────────────────┐
│      CATALOG MODULE     │
│                         │
│ CatalogController       │
│ CatalogService          │
│ DTOs                    │
│ related dependencies    │
│ tests                   │
└─────────────────────────┘
```

Your project intentionally organizes complex functionality around feature ownership and keeps controllers, services, DTOs, adapters, processors, queues and tests behind the feature that owns them.

# 12. Guard = security guard 🚨

Suppose someone requests:

```http
DELETE /admin/products/123
```

Should literally anybody on the internet be allowed to do that?

Obviously not.

Before the Controller executes, Ferio needs to ask:

```text
Who are you?

Are you logged in?

Are you allowed to delete products?

Do you belong to this tenant?
```

That's where **Guards** come in.

Conceptually:

```text
Request
   │
   ▼
 GUARD
   │
   ├── Allowed? → continue
   │
   └── Not allowed? → STOP ❌
```

---

# 13. Example

Suppose:

```text
Rahim
```

is an employee of:

```text
ABC Electronics
```

He requests:

```http
DELETE /products/123
```

Guard checks:

```text
Logged in?
    ↓
YES

Member of ABC?
    ↓
YES

Has permission PRODUCT_DELETE?
    ↓
YES

Continue ✅
```

Then Controller executes.

---

But another user:

```text
Logged in?
    ↓
YES

Member of ABC?
    ↓
NO

STOP ❌
```

The Controller should never get the opportunity to perform the deletion.

# 14. Ferio's TenantMembershipGuard

Your checklist specifically says protected Tenant Admin controllers are enforced with `TenantMembershipGuard`. 

The simplified idea is:

```text
Request says:
abc.ferio.com

Tenant Resolver:
"This is ABC."

Authenticated user:
"I am user 55."

TenantMembershipGuard:
"Is user 55 actually allowed inside ABC?"

       ↓

YES → continue

NO → 403 Forbidden
```

This is important because:

```text
Knowing a tenant exists
```

doesn't mean:

```text
You're allowed to administer that tenant.
```

# 16. Middleware

Now another strange word:

```text
Middleware
```

Middleware runs while the request is travelling through the application.

Think of an airport.

Before reaching your gate:

```text
Entrance
   ↓
passport/security
   ↓
terminal
   ↓
gate
```

Middleware can inspect/process requests early.

In your multi-tenant system, the tenant-resolution middleware is extremely important.

Remember Lesson 2?

```text
abc.ferio.com
      ↓
Who does this belong to?
      ↓
ABC
```

Your checklist says tenant middleware is wired across application routes except intentionally separate platform/health/socket paths. 

Simplified:

```text
HTTP Request

Host: abc.ferio.com
       │
       ▼
Tenant Middleware
       │
       ▼
Tenant Resolver
       │
       ▼
ABC found
       │
       ▼
Create TenantContext
       │
       ▼
continue request
```

# 17. Middleware vs Guard

This confuses many beginners.

Think:

### Middleware asks:

> **"What context does this request belong to?"**

For Ferio:

```text
abc.ferio.com
    ↓
tenant = ABC
```

### Guard asks:

> **"Is this person allowed to do this?"**

For example:

```text
User Yahya
    ↓
member of ABC?
    ↓
permission?
```

So:

```text
Middleware
    =
establish context


Guard
    =
authorize access
```

Not perfectly universal for every NestJS application, but it's an excellent mental model for **your Ferio architecture**.

# 18. DTO

Next scary acronym:

```text
DTO
```

It means:

**Data Transfer Object**

Ignore the fancy name.

Suppose frontend sends:

```json
{
  "name": "iPhone 17",
  "price": 120000,
  "stock": 50
}
```

Ferio needs rules:

```text
name must be text
price must be number
price can't be negative
stock must be integer
```

A DTO describes/validates the expected input shape.

Conceptually:

```ts
class CreateProductDto {

  name: string;

  price: number;

  stock: number;

}
```

So:

```text
Frontend
   │
   │ sends data
   ▼
 DTO validation
   │
   ├── valid → continue
   │
   └── invalid → reject ❌
```

---

# 19. Why DTO matters

Someone sends:

```json
{
  "name": "",
  "price": -50000000,
  "stock": "BANANA"
}
```

😂

You don't want that reaching your business logic.

DTO/validation layer says:

```text
NO ❌
```

So another piece appears:

```text
Request
   ↓
Middleware
   ↓
Guard
   ↓
DTO validation
   ↓
Controller
   ↓
Service
```

# 20. Prisma

You've seen Prisma many times.

Baby explanation:

> Prisma is the translator between your TypeScript backend and PostgreSQL.

Instead of manually writing:

```sql
SELECT *
FROM products
WHERE active = true
ORDER BY created_at DESC;
```

you can write something conceptually like:

```ts
db.product.findMany({
  where: {
    active: true
  }
});
```

Prisma talks to PostgreSQL for you.

So:

```text
NestJS Service
      │
      ▼
    Prisma
      │
      ▼
 PostgreSQL
```

# 29. Why your Ferio architecture can become complicated

Imagine `OrderService` starts depending on:

```text
OrderService
 ├── PaymentService
 ├── InventoryService
 ├── CustomerService
 ├── ShippingService
 ├── WalletService
 ├── NotificationService
 └── ReturnsService
```

Then PaymentService depends back on OrderService.

You get:

```text
OrderService
     ↓
PaymentService
     ↓
OrderService
     ↓
💥
```

That's the **dependency hell / circular dependency** we discussed earlier.

That's why your project structure rules emphasize keeping ownership and dependency boundaries visible instead of creating giant cross-feature utility dumps. 

We'll understand this much better once we follow an order in Lesson 7.
