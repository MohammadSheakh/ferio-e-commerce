# Lesson 5 — How Ferio Creates a New Business 🏪

Now we understand how an **existing tenant** works.

But imagine tomorrow a new company says:

> "I want to use Ferio."

Let's call them:

**Baby Shop BD**

They don't have anything yet:

```text
❌ Organization
❌ Database
❌ Domain
❌ Admin owner
❌ Settings
❌ Products
```

Ferio needs to transform that into:

```text
babyshop.ferio.com
        ↓
Baby Shop BD
        ↓
babyshop database
        ↓
Owner/Admin
        ↓
Ready to sell
```

This process is called:

# Provisioning

---

## 1. Provisioning in one sentence

**Provisioning = automatically preparing everything a new tenant needs to start using Ferio.**

Think about getting a new apartment.

You don't simply receive:

> Apartment 305 exists.

Before you move in:

```text
Apartment allocated
       ↓
Keys prepared
       ↓
Electricity connected
       ↓
Water connected
       ↓
Room checked
       ↓
You receive the key
```

Ferio does something similar for a tenant.

---

# 2. Where does creation start?

For your initial SaaS launch, your checklist says onboarding is intended to be **Platform Admin / sales-assisted initially**, rather than assuming completely self-service signup. 

So imagine you are Ferio Platform Admin.

You open:

```text
Ferio Platform Admin
```

and click:

```text

```

You enter:

```text

```

Then:

```text
                    CREATE
                       │
                       ▼
              Provisioning starts
```

# 3. Step 1 — Create Organization

Remember Lesson 3:

`Organization` belongs where?

### Control Plane. ✅

So Ferio creates something conceptually like:

```text
Organization
────────────────────────
id       org_babyshop
name     Baby Shop BD
slug     babyshop
status   PROVISIONING
```

Notice:

```text
status = PROVISIONING
```

Not:

```text
ACTIVE
```

Why?

Because the database doesn't even exist yet.

Ferio shouldn't tell customers:

> Your store is ready! 🎉

when half the infrastructure is missing.

---

# 4. Step 2 — Reserve the domain

Baby Shop wants:

```text
babyshop.ferio.com
```

Ferio must ensure another tenant doesn't already own it.

Control Plane checks:

```text
TenantDomain
```

Suppose:

```text
abc.ferio.com       → taken
perfect.ferio.com   → taken
babyshop.ferio.com  → available
```

Ferio reserves:

```text
babyshop.ferio.com
        ↓
org_babyshop
```

Now later when a request comes:

```text
Host: babyshop.ferio.com
```

the Tenant Resolver can know:

```text
This = Baby Shop BD
```

# 8. What is a database migration?

Don't let the word scare you.

Imagine the database is an empty building.

Migration says:

> Build these rooms.

```text
Empty DB
   ↓
Migration
   ↓
┌─────────────────┐
│ Product table   │
│ Order table     │
│ Customer table  │
│ Cart table      │
│ Payment table   │
│ Inventory table │
│ Settings table  │
│ ...             │
└─────────────────┘
```

In simple terms:

> **Database migration = changing the structure/schema of a database.**

For a new tenant, migrations build the database structure it needs.

---

# 9. Migration vs data

Important distinction.

Migration creates things such as:

```text
Product TABLE
```

It doesn't necessarily create:

```text
iPhone
Samsung
Blue Shirt
```

Think:

```text
Migration
   =
build the shelves


Data
   =
things sitting on the shelves
```

# 10. Step 4 — Seed the database

After migration:

```text
babyshop_db

Product table       empty
Order table         empty
Customer table      empty
Settings table      empty
```

But Ferio may need some initial/default records.

For example:

```text
Store settings
Default order statuses
Default configuration
Roles/permissions
Default delivery configuration
etc.
```

Creating initial data is called:

# Seeding

So:

```text
Migration
   ↓
creates STRUCTURE

Seed
   ↓
creates INITIAL DATA
```

Easy way to remember:

```text
Migration = build house 🏠

Seed = put basic furniture inside 🛋️
```

---

# 11. Why does your checklist say "business-neutral seed"?

Suppose your old single-store Ferio had:

```text
Store Name = Ferio Fashion
Phone = 017XXXXXXXX
Address = Dhaka
```

Hardcoded into seed data.

Now you create:

```text
Baby Shop BD
```

and suddenly its database says:

```text
Store Name:
Ferio Fashion
```

😂

Bad.

A SaaS seed should not accidentally contain another company's identity.

Your checklist specifically calls for an idempotent, **business-neutral** tenant seed. 

Meaning initial values should be safe/default values, while Baby Shop's actual branding/configuration comes from its own onboarding/settings.

# 17. What happens if you simply run everything again?

Bad provisioning:

```text
Retry
  ↓
Create Organization AGAIN
  ↓
💥 organization already exists

Create Domain AGAIN
  ↓
💥 domain already exists

Create DB AGAIN
  ↓
💥 database already exists
```

Now your system is confused.

This is why provisioning can't just be one giant:

```ts
doEverything();
```

and hope nothing goes wrong.

# 18. Enter: State Machine

Another scary term with a simple idea.

A state machine means:

> **Ferio remembers what state something is currently in and what transitions are allowed.**

For example:

```text
PENDING
   ↓
PROVISIONING
   ↓
READY
```

Or failure:

```text
PENDING
   ↓
PROVISIONING
   ↓
FAILED
```

Then:

```text
FAILED
   ↓
retry
   ↓
PROVISIONING
   ↓
READY
```

Ferio records progress rather than pretending everything happens magically at once.

Your control plane includes organization lifecycle history and provisioning run/step models for this kind of tracking.

# 19. Think of Domino's Pizza tracker 🍕

You order pizza.

It shows:

```text

Preparing            ✅

Quality check         ⏳

```

That's basically state tracking.

Provisioning can conceptually track:

```text

Migration             ✅
Seed                   ❌ FAILED
Owner                 ⬜
Health check          ⬜

```

# 20. Enter: Idempotency

This word appears everywhere in serious backend engineering.

### Idempotent means:

> Running the same operation again shouldn't accidentally create duplicate/broken results.

Baby example:

An elevator button.

You press:

```text
Floor 5
```

once.

Then 20 times:

```text
5
5
5
5
5
5
```

The elevator doesn't decide:

> He pressed it 6 times, so go to floor 30.

😂

The desired final state is still:

```text
Floor 5
```

That's the mental idea of idempotency.

---

# 21. Idempotent provisioning

First run:

```text
Organization   ✅
Domain         ✅
Database       ✅
Migration      ✅
Seed           ❌
```

Retry.

Ferio recognizes:

```text
Organization exists
       ↓
don't duplicate

Domain reserved
       ↓
don't duplicate

Database exists
       ↓
don't duplicate

Migration completed
       ↓
don't repeat unsafely

Seed incomplete
       ↓
continue/retry here
```

Then:

```text
Seed           ✅
Owner          ✅
Health check   ✅
Activate       ✅
```

Finished.

That's why your checklist describes the provisioning orchestrator as **idempotent and resumable**.

# 22. What is a Provisioning Orchestrator?

"Orchestrator" sounds very fancy.

Think about a music conductor. 🎼

The conductor doesn't personally play:

```text
piano
violin
drums
flute
```

The conductor coordinates them.

Likewise:

```text
ProvisioningOrchestrator
        │
        ├── Organization step
        ├── Domain step
        ├── Database step
        ├── Migration step
        ├── Seed step
        ├── Owner step
        └── Activation step
```

It says:

> Do step 1.

Done?

> Do step 2.

Done?

> Do step 3.

Failed?

> Record failure.

Retry later?

> Resume safely.

That's orchestration.


# 24. What about rollback?

Suppose provisioning creates:

```text
Organization ✅
Database     ✅
```

but something later catastrophically fails.

Should Ferio automatically delete everything?

Not necessarily.

Why?

Because deletion can make recovery worse.

Imagine:

```text
Migration completed
Seed partially completed
```

and the system immediately says:

```text
DELETE DATABASE
```

You just destroyed useful diagnostic state.

Often the safer model is:

```text
FAILED
  ↓
preserve evidence
  ↓
inspect/retry/recover
```

rather than blindly undoing everything.

That's why production provisioning needs explicit recovery behavior.

---

# 25. What if the same request arrives twice?

Suppose Platform Admin double-clicks:

```text
[ CREATE TENANT ]
[ CREATE TENANT ]
```

or the browser retries because the network was slow.

Without protection:

```text
Request 1 → create Baby Shop
Request 2 → create Baby Shop AGAIN
```

💥

You want:

```text
Request 1
    ↓
Provisioning operation XYZ


Request 2
    ↓
"Oh, XYZ already exists/in progress."
    ↓
Reuse/reject safely
```

This is another reason idempotency is so important.

```text

       ↓
```

```text
       ↓

```

Different responsibilities.

This means the software understands conceptually:


For example, eventually Ferio might tell some infrastructure/provider layer:


This is a good example of:


# 32. One final scenario

It's 3 AM.

Your autonomous Codex agent creates a test tenant.

It reaches:

```text
Organization        ✅
Domain              ✅
Database            ✅
Migration           ✅
Seed                ❌
```

PostgreSQL temporarily fails.

A **bad SaaS system** may leave a mysterious broken business forever.

A properly designed Ferio provisioning system should know:

```text
Baby Shop
    ↓
ProvisioningRun #928
    ↓
FAILED
    ↓
failedStep = SEED
    ↓
retain evidence
    ↓
retry safely
    ↓
don't duplicate completed resources
    ↓
continue
    ↓
health check
    ↓
READY
```

That is why all this "extra architecture" exists. It isn't complexity just for fun—it makes creating and operating many businesses recoverable.
