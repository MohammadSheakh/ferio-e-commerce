# Lesson 3 — Control Plane DB vs Tenant DB 🧠

This lesson answers one of the biggest questions in Ferio:

> **Why do we have two different kinds of databases, and what data goes where?**

We'll start extremely simple.

---

## 1. Imagine Ferio has 3 businesses

Suppose these businesses use Ferio:

```text
ABC Electronics
Perfect Textile
Fresh Mart
```

Each business needs its own data:

```text
ABC Electronics
├── Products
├── Customers
├── Orders
├── Inventory
└── Payments

Perfect Textile
├── Products
├── Customers
├── Orders
├── Inventory
└── Payments

Fresh Mart
├── Products
├── Customers
├── Orders
├── Inventory
└── Payments
```

Because you chose **database-per-tenant**, these become three databases.

```text
┌──────────────────┐
│ ABC DATABASE     │
│                  │
│ Products         │
│ Orders           │
│ Customers        │
│ Inventory        │
│ Payments         │
└──────────────────┘

┌──────────────────┐
│ PERFECT DATABASE │
│                  │
│ Products         │
│ Orders           │
│ Customers        │
│ Inventory        │
│ Payments         │
└──────────────────┘

┌──────────────────┐
│ FRESH DATABASE   │
│                  │
│ Products         │
│ Orders           │
│ Customers        │
│ Inventory        │
│ Payments         │
└──────────────────┘
```

Your target architecture explicitly requires an independently isolated PostgreSQL database for each tenant. 

So far, easy.

---

# 2. But who remembers that these businesses exist?

Now we hit a problem.

Imagine NestJS receives:

```text
abc.ferio.com
```

How does it know:

```text
ABC Electronics exists

AND

its database is ABC_DATABASE?
```

ABC's own database can't be the starting point.

Because to open ABC's database, Ferio first needs to know **which database belongs to ABC**.

😂 It's a chicken-and-egg problem.

We need another database.

That is your:

# CONTROL PLANE DATABASE

---

# 3. Think of the Control Plane as Ferio's brain

Imagine this:

```text
                   FERIO
                     │
                     ▼
            ┌─────────────────┐
            │  CONTROL PLANE  │
            │                 │
            │ "I know all     │
            │  businesses."   │
            └────────┬────────┘
                     │
          ┌──────────┼───────────┐
          ▼          ▼           ▼
        ABC DB    PERFECT DB   FRESH DB
```

The Control Plane knows:

```text
ABC exists
Perfect exists
Fresh exists

ABC's domain = abc.ferio.com
ABC's DB = DB_ABC

Perfect's domain = perfect.ferio.com
Perfect's DB = DB_PERFECT

Fresh's domain = fresh.ferio.com
Fresh's DB = DB_FRESH
```

---

# 4. The easiest rule

Memorize this:

> **Control Plane = information ABOUT the shops.**
>
> **Tenant DB = information INSIDE a shop.**

For example:

```text
"ABC Electronics uses Ferio"
              ↓
        CONTROL PLANE


"ABC Electronics received Order #1025"
              ↓
          ABC TENANT DB
```

That's the difference.

# 7. There's a very important money distinction

Suppose ABC sells an iPhone for:

```text
৳100,000
```

Customer pays ABC.

That is:

```text
CUSTOMER
   │
   │ ৳100,000
   ▼
ABC Electronics
```

This is **commerce payment**.

Therefore its records belong with ABC's commerce world:

```text
ABC TENANT DB
```

---

But ABC also pays Ferio:

```text
৳2,490/month
```

for the Ferio Business plan.

That's:

```text
ABC Electronics
       │
       │ ৳2,490
       ▼
     FERIO
```

Completely different money.

That's **SaaS billing**.

Therefore:

```text
CONTROL PLANE
```

So:

```text
Customer → ABC
     =
Commerce Payment
     =
Tenant DB


ABC → Ferio
     =
SaaS Payment
     =
Control Plane
```

Your checklist specifically requires platform billing and tenant commerce money to remain separate. 

This is a very important architectural boundary.

# 8. What does `Organization` mean?

In your project you'll see:

```text
Organization
```

a lot.

For our simple mental model:

> **Organization = the business/company using Ferio.**

Example:

```text
Organization

id: org_abc
name: ABC Electronics
slug: abc
status: ACTIVE
```

Another:

```text
id: org_perfect
name: Perfect Textile
slug: perfect
status: ACTIVE
```

So Control Plane might conceptually contain:

```text
Organization
────────────────────────────────
ID            Name
────────────────────────────────
org_abc       ABC Electronics
org_perfect   Perfect Textile
org_fresh     Fresh Mart
```

# 9. Then what is `TenantDatabase`?

This tells Ferio:

> Where is that organization's actual commerce database?

Conceptually:

```text
TenantDatabase
──────────────────────────────────────
Organization       Database
──────────────────────────────────────
org_abc            abc_db
org_perfect        perfect_db
org_fresh          fresh_db
```

So:

```text
Organization
      │
      ▼
TenantDatabase
      │
      ▼
actual PostgreSQL database
```

---

# 10. And `TenantDomain`?

This answers:

> Which internet address belongs to which organization?

Example:

```text
TenantDomain
───────────────────────────────────────
hostname                organization
───────────────────────────────────────
abc.ferio.com           org_abc
perfect.ferio.com       org_perfect
fresh.ferio.com         org_fresh
```

Now Lesson 2 should suddenly make even more sense.

Request:

```text
abc.ferio.com
```

Ferio does:

```text
abc.ferio.com
      ↓
TenantDomain
      ↓
org_abc
      ↓
TenantDatabase
      ↓
abc_db
```

💡 That's how the pieces connect.

# 14. What happens when Ferio gets 1,000 businesses?

This is where your architecture becomes interesting.

You could eventually have:

```text
Control Plane DB
       │
       ├── Tenant 1  → DB 1
       ├── Tenant 2  → DB 2
       ├── Tenant 3  → DB 3
       ├── ...
       └── Tenant 1000 → DB 1000
```

That does **NOT** mean NestJS should maintain 1,000 permanent Prisma connections all the time.

That would waste resources.

Instead your `TenantDatabaseManager` maintains a **bounded** collection of clients and can evict idle ones. Your current implementation specifically includes LRU-bounded clients and idle eviction. 

Baby analogy:

You own a hotel with 1,000 rooms.

You don't need to hold all 1,000 room keys in your hands.

You grab the keys you currently need.

```text
Current active DB clients

ABC       🔑
Perfect   🔑
Fresh     🔑
Shop X    🔑
```

If ABC hasn't had traffic for a while:

```text
ABC 🔑 → release
```

Later someone visits ABC:

```text
abc.ferio.com
      ↓
Need ABC DB
      ↓
create/reuse connection
```

We'll get deeper into connection pooling later.

# 15. Why can't Tenant DB directly foreign-key Control Plane?

This is another important concept from your architecture. Your classification explicitly prohibits tenant-database foreign keys to control-plane tables. 

Imagine ABC DB contains:

```text
Order
```

and you try:

```text
Order.organizationId
       │
       │ FOREIGN KEY
       ▼
ControlPlane.Organization
```

Problem:

Those tables live in **different databases**.

```text
ABC DATABASE

Order
```

versus:

```text
CONTROL PLANE DATABASE

Organization
```

You shouldn't design normal relational foreign keys across that boundary.

Instead, when necessary, you carry an **opaque identifier**.

Something like:

```text
organizationId = org_abc
```

Think of it like writing someone's passport number on a form.

The form can reference the number.

It doesn't physically contain the passport office's database.

# 16. Why is isolation so powerful?

Suppose someone somehow runs:

```sql
DELETE FROM orders;
```

against ABC's tenant DB.

That's terrible for ABC.

But because Perfect Textile lives in:

```text
perfect_db
```

its orders aren't in ABC's database.

So the damage boundary is stronger:

```text
ABC DB 💥

Perfect DB ✅
Fresh DB   ✅
Fashion DB ✅
```

Database-per-tenant doesn't magically solve every security problem, but this isolation is one major reason for choosing it.

---

# 17. It also helps backup/restore

Imagine ABC accidentally destroys its catalog.

With tenant-independent backup/restore, conceptually:

```text
ABC DB
   ↓
restore ABC backup
```

without having to restore:

```text
Perfect
Fresh
Fashion
BabyShop
...
```

Your project's final Definition of Done specifically requires proving that one tenant can be backed up/restored independently. 

That's later work in MT-12.
