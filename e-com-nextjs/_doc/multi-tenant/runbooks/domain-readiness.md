# Domain Readiness Runbook

This runbook verifies a custom domain before an operator activates it. The
check is deliberately separate from ownership-token activation so a domain
cannot become traffic-visible merely because a TXT challenge was presented.

## Preconditions

- The hostname is present in the platform registry and belongs to the expected
  organization.
- The ownership token was generated by the platform and was not copied into
  logs, tickets, or chat.
- The operator has a controlled maintenance shell with outbound DNS and TCP
  443 access.

## Verification

From `e-com-nextjs/ferio-nest-prisma` run:

```sh
pnpm verify:domain-readiness -- shop.example.com 'ferio-verify=<token>'
```

The command requires all of the following:

1. The hostname resolves to at least one address.
2. `_ferio-verification.<hostname>` contains the exact generated token.
3. TLS on port 443 completes with a publicly trusted certificate whose
   hostname is validated by Node's TLS client.

An optional third argument pins the expected address during a cutover:

```sh
pnpm verify:domain-readiness -- shop.example.com 'ferio-verify=<token>' 203.0.113.10
```

## Activation procedure

1. Record the verifier JSON output, operator, timestamp, registry domain ID,
   and organization ID in the change ticket.
2. If any check fails, leave the domain `PENDING_VERIFICATION` or
   `VERIFICATION_FAILED`; do not activate it and do not add it to a routing
   allowlist.
3. After the DNS/TLS evidence is reviewed, call the organization-scoped domain
   verification endpoint with the ownership token.
4. Confirm the hostname resolves to the intended tenant and that the storefront
   returns that tenant's branding before setting it primary.
5. Remove the token from the shell history and ticket after the evidence is
   recorded. Store only the verifier result, never the token.

This command is an operator verification contract. It does not create DNS
records, issue certificates, or replace provider-side monitoring and renewal
alerts.
